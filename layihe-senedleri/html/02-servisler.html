1. infra — Paylaşılan Kitabxana

Spring Boot deyil, sadə java-library jar-ıdır. Spring asılılığı yoxdur — yüngül qalsın deyə. Bütün servislərin paylaşdığı tipləri saxlayır və ./gradlew publishToMavenLocal ilə mavenLocal()-a yerləşdirilir.

Tərkibi

  • 8 enum: UserRole, PolicyStatus, ClaimStatus, ClaimType, PaymentStatus, PaymentReferenceType, NotificationType, NotificationChannel.
  • 8 event DTO (record): UserRegistered, PolicyCreated, PaymentCompleted, PaymentFailed, ClaimSubmitted, ClaimDecision, FraudDetected, Notification.
  • KafkaTopics sabitləri — topic adları heç vaxt sətir kimi hardcode edilmir.
  • Cavab zərfləri: ApiResponse<T>, PagedResponse<T>, ErrorResponse.
  • Exception modeli: BaseErrorService interfeysi + BaseErrorEnum + BaseException və 4 hazır alt-sinif + ServiceException.
  • DateUtil: bütün vaxtlar Instant ilə işlənir, LocalDateTime yox.
Niyə vacibdir: Bütün servislər eyni event və enum tiplərini import edir — heç bir tip dublikat olunmur. Bir hadisənin formatı dəyişəndə yalnız infra-da dəyişir.

2. gateway — API Gateway

Spring Cloud Gateway (reaktiv/WebFlux) üzərində qurulub. Bazası yoxdur — sırf marşrutlama və autentifikasiya çoxluğudur. infra-dan asılı deyil.

Necə işləyir

  • JwtAuthFilter (order = -1, marşrutlamadan əvvəl): yolu public siyahıya görə yoxlayır.
  • Public yollar: /api/v1/auth/** (hər metod) və /api/v1/plans/** (yalnız GET).
  • Qalan yollar üçün Authorization: Bearer <token> tələb olunur; yoxdursa/yanlışdırsa → 401.
  • Doğru token-də sorğuya X-User-Id və X-User-Role başlıqları əlavə olunur.

4. policy — Planlar və Police-lər

İki entity: Plan (sığorta məhsulu kataloqu) və Policy (müştərinin aldığı konkret müqavilə). Plan qiyməti alış anında police-yə kopyalanır ki, sonrakı qiymət dəyişikliyi köhnə police-lərə təsir etməsin.

Plan

name, description, coverageAmount, premiumAmount, durationMonths, active

Policy

policyNumber (POL-xxxx), userId, plan (ManyToOne), status, premiumAmount, startDate, endDate

Police həyat dövrü

Alış → PENDING (startDate/endDate boş) → ödəniş tamamlananda → ACTIVE (endDate = start + durationMonths). Ləğv yalnız PENDING/ACTIVE-dən mümkündür → CANCELLED.

5. claim — İddialar

Sistemin mərkəzi. Müştəri iddia göndərir, AI avtomatik qiymətləndirir, lazım gələrsə əməkdaş yoxlayır. Sübut faylları (multipart) diskdə saxlanılır.

Entity: Claim (claims)

claimNumber (CLM-xxxx), userId, policyId, claimType, amount, description, status, approvedAmount, rejectionReason, reviewedBy, riskScore, fraudFlags, aiExplanation. Ayrıca ClaimEvidence (fayl metadatası).

AI avtomatik qərar (applyFraudResult)

fraud.detected qəbul edildikdə risk balına görə avtomatik qərar verilir. Status SUBMITTED deyilsə heç nə edilmir (manual baxış üzərinə yazılmır):

< 40APPROVEDTam məbləğ təsdiqlənir, claim.decision yayımlanır
40–69UNDER_REVIEWƏməkdaş növbəsinə düşür (event yox)
≥ 70REJECTEDRədd edilir, claim.decision yayımlanır

Manual baxış (reviewClaim): yalnız STAFF/ADMIN, yalnız SUBMITTED/UNDER_REVIEW statusda. APPROVED üçün 0 < approvedAmount ≤ amount tələb olunur.

Kafka: göndərişdə claim.submitted; qərarda (manual və ya AI) claim.decision; fraud.detected qəbul edir.

6. payment — Ödəniş (Mock)

MVP üçün ödəniş simulyasiyadır: MockPaymentProcessor 2 saniyə gecikir, sonra avtomatik COMPLETED edir. İki istiqamətdə işləyir — premium ödənişi (police üçün) və iddia ödənişi (müştəriyə).

Entity: Payment

userId, referenceId (policyId və ya claimId), referenceType (POLICY_PREMIUM / CLAIM_PAYOUT), amount, status, transactionId (TXN-xxxx), failureReason.

İdempotentlik (kritik düzəliş): processPayment əvvəlcə eyni (referenceId, referenceType) üçün FAILED olmayan ödəniş axtarır — varsa, yenisini yaratmadan mövcudu qaytarır. Bu, Kafka təkrar çatdırılması zamanı ikiqat ödənişin qarşısını alır.

Kafka: policy.created → POLICY_PREMIUM ödənişi; claim.decision (yalnız APPROVED) → CLAIM_PAYOUT; nəticədə payment.completed və ya payment.failed yayımlanır.

7. ai — Fırıldaq, Risk və Chatbot

Üç vəzifəni daşıyır. claim.submitted qəbul edib hibrid fırıldaq qiymətləndirməsi aparır və fraud.detected yayımlayır.

Hibrid fırıldaq aşkarlanması

  • Qayda mühərriki (rule engine): claimType üzrə məbləğ hədləri (HOSPITALIZATION 10000, MEDICATION 2000, DENTAL 1500, CONSULTATION 500) + təkrar yüksək-riskli istifadəçi yoxlaması → ruleScore.
  • AI çağırışı: yalnız ruleScore ≥ 40 olduqda OpenRouter/Gemini 2.5 Flash çağırılır. Cavab markdown ``` fence-lərindən təmizlənib JSON kimi parse olunur.
  • Yekun bal: AI işləyibsə finalScore = ruleScore×0.4 + aiScore×0.6, əks halda yalnız ruleScore.
  • Fallback: AI xətası/timeout olarsa (default 15s) sırf qaydaya əsaslanan bala düşür — sistem dayanmır.

Digər iki vəzifə

  • RiskProfile: hər istifadəçi üçün bir sətir — totalClaims, averageRiskScore, highRiskCount. highRiskCount ≥ 2 = yüksək riskli.
  • Chatbot: sessiya tarixçəsi ilə çoxnövbəli söhbət (ChatMessage), sığorta köməkçisi personası.

Tək istiqamətli: 7 hadisənin hamısını qəbul edir, heç nə yayımlamır. Hər hadisəni uyğun bildiriş tipinə çevirir. MVP-də real email/SMS yoxdur — NotificationSender sadəcə log.info ilə "göndərir" və SENT statusu qoyur.
